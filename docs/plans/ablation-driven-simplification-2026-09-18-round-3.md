# Momentum 第三轮消融：从局部结构转向状态所有权

## 基线与实验设计

基线为 `a0eba9ec3c32fa23d97de73da8875483f7616085`（第二轮消融），
工作区干净，Node 20.19.0。
全量基线：250 文件，1,873 通过 / 1 失败；失败仍为 RSIP 原子创建接线。
本轮不改这条持久化链路，不把既有失败移出测试发现范围。

以下候选在生产修改前登记。目标是减少真实流程的状态来源及同步责任，而非追求
删除行数；上一轮已证明有价值的构树 memo、mounted callback、平台错误合同及
缺列 fallback 不重复试删。

| 候选                       | 假设与可逆操作                                                                                                                       | 接受/拒绝依据                                                                                  |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------- |
| 服务层乐观创建及状态镜像   | 真实 UI 等待 createRule/createChainRule，管理页乐观更新另有所有者；去掉无人调用的 temp ID API、三张 Map、清理计时器及其诊断/恢复分支 | 持久化 ID 创建后立即执行、失败不记使用、缺失/停用/错类型仍拒绝；保留实际 UI 乐观更新及数据修复 |
| 规则选择快照与重复检测 TTL | 缓存缺失 actionType / mutation 失效；直接读持久化、以 React state 展示列表                                                           | 先复现切换动作、重命名/删除后检查的陈旧结果；测量直接检查成本，再决定是否保留                  |
| 搜索索引/结果缓存          | 与存储快照缓存分开评估，不能因二者都叫 cache 就一起删除                                                                              | 对相同规则集比较命中、重新查询、重建索引成本；没有收益证据不扩大改动                           |
| 架构门禁测试 fixture       | 在隔离目录执行真实规则即可验证拦截，不必向源码写文件并重扫全仓                                                                       | 允许的 public port 通过；违规 UI import 和循环失败且命中正确规则；完整架构门禁仍单独执行       |

静态复核同时覆盖 AppShell/domain/storage/platform/quality。RSIP 创建涉及原子保存与
恢复日志，单独处理；不为追求一个全绿结果扩大本轮数据写入变更。

## 实验记录

### E1：删除服务层乐观创建及其自我维护链

调用追踪覆盖整个 `src` 的静态/动态入口，并区分历史实验代码与生产代码：

- `RuleSelectionDialog`、默认规则流程调用 `createChainRule`；
  focus-mode、规则管理页调用 `createRule`，均等待持久化返回。
- 管理页 `useRuleManagerActions` 的临时展示 ID 为 `create-rule-*`，自己负责替换与
  失败回滚；它不调用 `createRuleOptimistic`。这一套 UI 行为及测试保持不变。
- `createRuleOptimistic` 仅由 manager 转发给 creator，再进入 RuleStateManager；
  没有生产调用入口。其 `temp_*` 映射只有内存 Map，不是持久化字段、导入格式或
  跨刷新恢复协议；真实 RulePersistence 在保存时生成 `rule_*` ID。
- 执行入口为支持该闲置路径而先验证/映射 ID，再读取存储，然后进行实际分类验证。
  初始化、健康检查及所谓通用恢复又为这份镜像提供同步和诊断。

实验删除整个服务层协议：两个乐观 API、三张 Map、ID counter、五分钟清理任务、
初始化同步、临时规则恢复、镜像健康检查；不再只合并它内部的类。
执行直接读取存储，保留 missing/inactive/type mismatch 验证、缺类型修复及使用记录。

先新增的持久化 ID/删除行为两条回归在基线 **30/30** 通过；消融后，services +
真实 UI action hooks + lifecycle 共 **39 文件 / 335 项通过**。新增第三条验证存储故障
不产生使用记录。旧预检吞掉存储错误并伪装为 RULE_NOT_FOUND；现在由 executor
报告 STORAGE_ERROR，这是有意的错误分类修正。

第一次回归只有健康报告仍要求五个组件的断言失败。删除的组件只衡量不存在的状态
镜像，改为验证四个实际组件。平均分分母从 5 变为 4，quick check 也不再扣镜像错误
分数；**前后健康分数不能作为质量提升指标**。未知错误的恢复选项改为已有的数据
完整性检查，名称同步更新；不再复制状态后宣称“已恢复”。真实修复功能保留。

### E2：移除两个陈旧快照及最后的缓存框架

先增加回归再改生产代码：**4 失败 / 27 通过**。

| 场景                                   | 原实现实际失败           | 消融后                 |
| -------------------------------------- | ------------------------ | ---------------------- |
| 同一链由 pause 切换到 early_completion | chainId 缓存返回暂停规则 | 重新按链和操作类型筛选 |
| 重命名后重新加载列表                   | 仍显示 Original          | 显示 Renamed           |
| 重命名后重复检测                       | 旧名称仍报冲突           | 当前存储决定冲突       |
| 删除后重复检测                         | 仍提供旧规则供复用       | 不再提供失效规则       |

`useRuleSelectionRules` 直接加载，React state 持有展示列表；保留 addRule 的链/作用域
约束。过滤额外检查 `isActive`，确保软删除规则不会出现在重新加载的列表中。
`EnhancedDuplicationHandler` 保留全部冲突判定、名称建议和创建选择，只去掉结果 TTL
和四处失效通知。存储层的重复名称检查未改，直接检测失败仍有原异常/降级合同。

这两个生产消费者移除后，ExceptionRuleCache/CacheCore 已没有剩余消费者。因此删除
其 namespace、TTL、subscriber、stats、eviction、preload 等整套框架、常量和一分钟
清理任务，而非搬到新的通用模块中。规则搜索缓存、Supabase 缺列缓存、taskTimeStats
缓存、持久化数据均未改。

消融后相关 **39 文件 / 356 项通过**，包含规则选择 UI、真实本地存储 hook 回归、
规则服务与搜索算法。原缓存生命周期测试随已删除实现退休，不用它们证明产品正确；
新测试针对真实的用户可见陈旧结果。

### E3：拒绝连带删除搜索复用

没有因为删除 E2 的快照就把所有搜索优化一并删除。临时探针分别运行：

1. 同一数组、同一 query 的缓存命中。
2. 每次先 `optimizer.clearCache()`，保留索引，强制重新搜索。
3. 每次传入 `[...rules]`，强制重建索引并搜索。

这些是计算路径消融，不是另一次生产代码重写。10,000 条规则时，较宽的搜索在
去结果缓存后约 **13.8ms**，重建索引后约 **47.6ms**；命中约 0.0002ms。
结果缓存和索引都有可测收益，本轮保留整个现有搜索实现。此证据不证明搜索历史、
热门建议等其他 API 都有生产价值，也不把“保留当前实现”当成算法最优的证明。

### E4：隔离架构门禁实验

原 repo-governance 在 `src/components` 创建违规文件，另一个 cycle 测试还把临时
目录追加到 npm 命令的固定 `src` 后，两者均扫描全仓。上一轮已有与 Knip 并行冲突。

改为在临时目录建立少量 TS fixture，以真实 dependency-cruiser CLI 和仓库中的真实
`.dependency-cruiser.cjs` 检查。正对照 public storage port 成功；UI → Supabase 与
循环依赖分别以状态 1 失败并报告对应规则。每次 finally 清理，CLI 失败/超时不会被
当作成功拦截。完整 `quality:arch-gate`、配置和 CI 命令保持原样并单独验证。

**13/13 通过**。本轮基线该文件 8.860s（全套运行中），修改后单独运行 1.216s，
最终并行验证中 2.790s。环境负载不同，不宣称稳定加速比例；确定消失的是源码写入
副作用及两次全仓重扫。

## 性能方法与限制

临时 Vitest 探针使用真实 `process.hrtime.bigint()`，每个场景热身 5 次、记录 30 次；
median 取排序后第 16 项，p95 取第 29 项。没有固定毫秒门禁。
规则为 10/100/1,000/10,000 个合法 chain-scoped 记录，ID `rule-i`，名称
`Focus break`、一个空格和五位序号，usageCount 为 i % 10，日期为 2026-01-01。
以真实 localPreferences 序列化保存，重复检测使用真实 storage 读取/日期解析。
两种 query 为 `Focus break 00005`（表中 exact）和 `Water`（表中 broad）。
均为合成压力数据，**没有真实用户规模、命中率、中文语料分布或真机延迟证据**。

## 实际结构变化

与上一轮相同口径：生产 TS/TSX 含 `.d.ts`，排除 test/**tests**/fixtures 与
`.test.`/`.spec.` 文件；物理行数含空行、注释，忽略文件末尾空白。
class/interface 计 AST declaration；before 读取 HEAD，after 读取工作区。

| 指标            |  Before |   After |    差值 |
| --------------- | ------: | ------: | ------: |
| 生产 LOC        |  61,973 |  60,835 |  -1,138 |
| 生产文件        |     658 |     650 |      -8 |
| class           |      74 |      71 |      -3 |
| interface       |     433 |     426 |      -7 |
| 测试/辅助 LOC   |  55,662 |  54,629 |  -1,033 |
| 测试/辅助文件   |     270 |     267 |      -3 |
| JS chunks       |      46 |      46 |       0 |

| gzip bytes 总和 | 290,005 | 286,416 |  -3,589 |

没有新服务、通用 registry、npm 依赖、定时任务或存储迁移。两项清理计时器随它们
拥有的状态一起消失；保留真实任务 timer。没有按文件长度重新拆分模块。

构建比较为同一 Web 配置的 `dist/assets/*.js`，每个 chunk 使用 gzip level 9 再求和，
排除 service worker/source map；这不是一次导航下载量，也不是交互性能。

测试数变化可解释：删除 RuleState 的 5 项、CacheCore 的 25 项、ExceptionRuleCache
的 19 项，以及镜像健康/恢复/ID 解析的 4 项；重复检测移除 3 项缓存机制测试、增加
2 项新鲜度测试；manager 增加 3 项、selection hook 增加 3 项。单测净减 **48**。
集成 suite 另删除 8 项仅互测两个已删除缓存类的测试。保留实际本地、Supabase SDK +
MSW、分类验证、UI 乐观回滚和数据修复测试；没有改测试发现配置或任何阈值。

## 停止条件与下一步

本轮停止于三个有证据的结构变更：删除不可达的服务层状态协议、去掉会提供陈旧数据
的额外快照、隔离治理测试。没有继续机械删除剩余 class 或所有缓存。

下一步优先级按实际影响排序：

1. **RSIP 原子创建接线**：连续多轮复现的真实正确性问题，比下一层转发删减重要；
   应以失败/重试时 nodes 与 metadata 同时可见为验收条件，单独处理其持久化链路。
2. **大规则库与查询变化**：先量真实规模、创建的重复扫描和 debounce 取消/旧结果
   覆盖风险；保留有测量收益的索引，进一步实验需同时验证排序、高亮和结果新鲜度。
3. **剩余诊断/恢复体系**：本轮只切除了以已删除镜像为目标的分支。其他统计、评分、
   export/import setter 等是否值得存在仍需生产消费者和有效恢复证据，不因本轮成功
   就宣称全部必要或全部可删。
