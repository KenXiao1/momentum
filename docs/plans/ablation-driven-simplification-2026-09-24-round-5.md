# Momentum 第五轮消融：创建意图与操作结果

## 基线与预登记

基线为 `bfe2e75`，工作区干净，Node 20.19.0。本轮延续第四轮留下的候选，
以当前代码为准：后续审计提交已加强 RSIP/import/session 事务，不重复改写这些链路。

| 实验                  | 假设与操作                                                                                                                           | 接受条件                                                                                                                                  |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------- |
| E1 重复创建预检查     | 专注模式先查重、按第一条建议自动选择，再创建时重新查重；把“精确重用、相似创建”意图交给创建服务，删除 UI 预读和唯一消费的实时检查 API | 真实 UI hook → manager → local storage 前后验证精确复用、相似创建、无冲突创建、类型验证及失败；保留存储最终重复检查和其他调用者的显式选择 |
| E2 平台操作回调       | 四类操作通过 callback 读取全量能力，再取本项 adapter；直接读取本项 adapter，删除 factory 反向回调                                    | 权限变化、unsupported/cancel/failure 合同保持；无关 adapter 故障不阻止当前操作                                                            |
| E3 恢复历史与成功判定 | 两份内存恢复历史无消费者；修复数据完整性不能证明原操作已完成                                                                         | 删除历史不影响真实修复；修复后数据可读回，原失败操作未重试时不能向 UI 报告操作成功                                                        |

先运行相关基线并固定可观察行为，再修改生产代码。不新增持久化缓存、依赖、
定时服务、SQL migration，不调整测试发现范围或质量门槛。

## 实验结果

原始全量单测基线：**262 文件 / 1,946 项通过**。下面各实验的定向数量是子集，
不可相加当作最终测试总数。

### E1：用创建意图替代预检查协议

调用追踪确认 `checkRuleNameRealTime` 只有专注模式一个生产消费者。它不是随输入
触发的交互检查，而是在提交时取 `suggestions[0].type`，随后再调用创建入口。
当前建议顺序固定为精确重复 → `use_existing`，相似名称 → `create_anyway`。

修改前新增真实 hook → manager → creator → repository → localPreferences 回归，
**11 项全部通过**。另在 manager 的真实存储测试里固定显式改名和相似规则复用行为。

- 专注模式直接传 `reuse_exact`。创建服务在本次查重结果上决定精确复用或相似创建，
  不再用前一份 UI 查重结果决定后一次操作。
- 删除 manager/creator/handler 三层实时检查方法、两个重复返回接口、恒为 false 的
  `isChecking`、建议字段复制与四个无消费者的 suggestion handler 闭包。
- 以一个 `DuplicateResolution` 类型表达创建选择，去掉从未生成的 `merge_rules`。
- 保留输入验证、默认重复异常、显式改名/复用/继续创建、名称建议、相似警告及
  repository 写入前的最终重复检查。链专属创建、规则搜索索引和缓存均未改。

修改后同一组真实行为回归通过：精确名称及大小写/空白归一化复用原 ID；相似名称
原名创建并提示；无冲突创建；空白/超长名称拒绝；非法类型按当前动作归一化；
已有规则类型不允许暂停时不写使用记录、不暂停；坏 JSON 和存储边界写失败保留流程。
原来的六项实时检查测试和一项转发测试随 API 删除，错误/冲突行为由真实流程及现存
完整检查测试承担，没有放宽存储或最终使用验证。

**接受**。已初始化且成功的新建路径少一次全库读取和一次重复计算；没有做本轮
耗时测量，不宣称用户可感知提速。移除的预检查曾吞错后再扫描，偶发预读失败可能
被第二次扫描掩盖；现在创建读取失败通过原错误流程处理，未保留这次隐式重试。
没有引入快照复用或跨请求缓存，也不声称解决跨标签并发。

### E2：平台操作只依赖自己的 adapter

基线平台及消费者 **13 文件 / 75 项通过**。四个 factory 没有实例状态，每次操作
通过 callback 回到 center，加载四种 adapter，再次取得当前操作的 adapter。

新增四项反证：让其余 adapter 的加载失败，当前可用的 notification/window/file/
haptics 操作在旧实现上全部失败。另两项固定通知总体支持和具体操作 flag 必须
同时成立。消融后 **13 文件 / 81 项通过**。

删除四个 factory 和四条回到 center 的回调，改为模块对象；每次操作取得自己的
adapter 后读取能力并执行。保留聚合 `getCapabilities`、动态权限查询和原生 lazy
import。文件取消/失败、窗口与触觉失败、通知不支持的合同仍由已有测试验证。

**接受**。生产 LOC 增加 2 行，是局部 adapter 变量的成本；收益是减少依赖及无关
故障传播。没有删除第二轮已证明必要的操作包装，也没有做原生 IPC 性能测量。
本项不改变当前 adapter 自身加载异常的传播合同。

### E3：删除无消费者历史，区分修复与操作成功

全仓调用追踪未发现 `recoveryHistory`、`fixHistory` 及其 getter/clearer 的消费者。
这两份无界数组只复制已返回的结果，并长期保留错误、上下文及 action 闭包。
删除两个字段、相关写入/方法和 `RecoveryHistoryEntry`；每次返回值与真实修复保持。

定向基线 **8 文件 / 48 项通过**。新增真实持久化恢复回归 **2 失败 / 1 通过**：

| 场景                                      | 修改前                   | 修改后                         |
| ----------------------------------------- | ------------------------ | ------------------------------ |
| usageCount 与使用记录不一致，自动修复成功 | 落盘修复后返回原操作成功 | 修复仍落盘，要求重试原操作     |
| focus 使用失败后修复无关数据              | 清除原错误并提示已解决   | 保留原错误，不暂停、不结束流程 |
| 修复本身写失败                            | 保留原数据、要求用户操作 | 继续保持                       |

存储策略现在返回 `success: false`、`requiresUserAction` 和已有重试选项，同时保留
修复数量并说明需要重试。明确的数据修复 action 仍可对自身修复返回成功；不能把
那个成功扩大为尚未重放的原创建/使用操作成功。修改后相关 **9 文件 / 51 项通过**。

**接受**。组合测试的 manager/integrity/repository 使用真实实现；focus 测试仅在
原 `useRule` 操作边界注入失败，以验证真实恢复结果如何影响界面反馈。创建组合
测试则固定 recovery 为失败，分别验证职责，未声称整套恢复策略已获正确性证明。
